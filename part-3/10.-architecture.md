# 10. 시스템 구성과 데이터 흐름

화면에 숫자가 왜 그렇게 나오는지, 고객 질문에 왜 그렇게 답해야 하는지는 이 구조를 알아야 설명할 수 있습니다.

## 전체 구성

```
 [고객사 내부망]                           │        [모노 클라우드]
                                          │
 ┌──────────────────────────┐  Outbound   │   ┌──────────┐   ┌──────────────┐
 │ Odyssey / Twoway / CS    │  HTTP(S)    │   │ Gateway  │──►│ poseidon-api │
 │ M2X  + Cypher (오류 수집) │ ──────────► │──►│ (인증)    │   │   + DB       │
 └──────────────────────────┘             │   └──────────┘   └──────┬───────┘
        ▲                                 │                         │
        │ 발송/수신                        │           ┌─────────────┴─────────┐
 ┌──────┴──────┐                          │           ▼                       ▼
 │  고객사 DB   │                          │    Poseidon Ops 화면        RabbitMQ → Rust
 └─────────────┘                          │    (상태·이벤트·오류)        → Prometheus (지표)
                                          │
                                          │  ※ Poseidon → 고객사 방향 접속은 없음
```

### 고객사 쪽 (설치되는 것)

| 이름 | 정체 | 역할 |
| --- | --- | --- |
| **Odyssey** | 문자·RCS·카카오 **발송** 엔진 (Java) | 발송 + 기동·하트비트·종료 신호 전송 |
| **Twoway** | **수신**(양방향) 엔진 | Odyssey와 동일한 방식으로 연동 |
| **CS** | 데스크톱 메시징 클라이언트 | 머신·앱 정보와 상태 신호 전송 |
| **M2X** | 레거시 제품 | **자체 신호 없음** — Cypher 사이드카가 대신 상태를 알림 |
| **Cypher (EMBEDDED)** | 네이티브 라이브러리 (`cypher.dll` / `libcypher.so`) | 엔진과 **같은 프로세스**에서 ERROR/FATAL 로그를 가로채 보고 |
| **Cypher (SIDECAR)** | 별도 프로세스 | 레거시(M2X)에 붙여 **로그 파일과 `.alive` 파일을 감시** |

{% hint style="info" %}
Cypher 모드는 화면의 **인스턴스 상세 → 개요 → Cypher 에이전트** 카드에서 확인합니다. `EMBEDDED`인지 `SIDECAR`인지에 따라 보이는 항목과 상태 판정 방식이 다릅니다.
{% endhint %}

### 우리 쪽

| 이름 | 역할 |
| --- | --- |
| **Gateway** | 외부 진입점. 고객이 보낸 인증 키를 검증해 고객사·인스턴스 식별값으로 변환 |
| **poseidon-api** | 본체. 인스턴스 등록, 하트비트·오류 저장, 상태 판정, 알림 발행, 지표 중계 |
| **DB** | 인스턴스·오류·이벤트 이력 저장 → **화면이 보여주는 데이터** |
| **RabbitMQ → Rust → Prometheus** | 지표(그래프) 전용 경로 |
| **Poseidon Ops** | 고객지원팀이 보는 화면 (이 매뉴얼의 대상) |

{% hint style="warning" %}
**상태·오류와 지표는 경로가 다릅니다.** 상태·오류·이벤트는 `poseidon-api → DB → 화면`으로 흐르고, 지표(그래프)는 `RabbitMQ → Rust → Prometheus`로 흐릅니다. 그래서 **"상태는 UP인데 지표만 비어 있는"** 상황이 생길 수 있고, 이건 고객사 문제가 아니라 우리 쪽 지표 파이프라인 문제일 수 있습니다 ([16. 플레이북 C](../part-4/16.-playbook.md)).
{% endhint %}

## 고객사가 보내는 신호 4가지

| 시점 | 신호 | 화면에 반영되는 곳 |
| --- | --- | --- |
| 기동 시 1회 | **기동 등록** | 인스턴스 목록에 나타남 + 이벤트 `서비스 시작` |
| **30초마다** | **하트비트** (지표 동봉) | 상태 `UP` 유지, `하트비트` 열 갱신, 지표 그래프 |
| 종료 시 1회 | **종료 알림** | 이벤트 `서비스 종료` — **계획된 종료로 기록, 장애 알림 아님** |
| 오류 발생 시 | **오류 보고** | 인스턴스 상세 `에러` 탭 + 이벤트 `에러 수신` |

* 인증은 요청마다 **인증 키(API Key) 헤더 1개**로 이루어집니다. 고객사에 별도 인증서·VPN·계정은 필요 없습니다.
* 하트비트 1회 크기는 **300\~500바이트**, 트래픽은 **하루 약 1\~1.5MB** 입니다.
* 전송 실패는 고객사 로그에 경고만 남고 **발송에는 영향이 없습니다**(다음 주기에 재시도).

## 순서대로 보면

```
1) 고객사가 엔진 기동
      │
      ├─► 기동 등록 ──► Gateway 인증 ──► DB 등록
      │                                 └─► 인스턴스 화면에 등장 (UP)
      │                                     이벤트: 서비스 시작
2) 이후 30초마다
      ├─► 하트비트 + 지표 ──► 하트비트 시각 갱신
      │                       └─► 지표는 RabbitMQ로 넘겨 그래프로
      │
3) ERROR/FATAL 로그 발생 시
      ├─► 오류 보고 ──► 오류 저장 + 이벤트 생성 ──► 알림 발송
      │                                           └─► 인스턴스 상세 '에러' 탭
      │
4) 3분 넘게 하트비트가 안 오면
      └─► 서버가 자체 판단으로 DOWN 처리 + 장애 알림
                                          └─► 이벤트: 하트비트 타임아웃
```

## 화면이 데이터를 가져오는 방식

문의 대응 중 "화면이 안 나온다"는 상황을 구분하는 데 필요합니다.

| 화면 | 조회 대상 |
| --- | --- |
| 대시보드 | 요약 + 이벤트 20건 + 전체 인스턴스 + 고객사 목록 (**4개를 동시에** 조회) |
| 인스턴스 | 통합 인스턴스 목록 |
| 인스턴스 상세 | 인스턴스 1건 + 에러 + 이벤트 + 고객사 목록 |
| 이벤트 | 이벤트 최대 500건 |
| 고객사 | 고객사 목록 (20건 페이지) |
| 인스턴스 관리 / 사용자 | 관리자 전용 목록 |

{% hint style="info" %}
대시보드는 4개 조회를 병렬로 실행합니다. 그래서 **일부만 실패하면 화면의 일부 카드만 비고 나머지는 정상**으로 보일 수 있습니다. 예를 들어 요약 조회만 실패하면 `대시보드 요약 데이터를 불러오지 못했습니다.` 토스트가 뜨면서 KPI만 비고 고객사별 인스턴스는 그대로 나옵니다.
{% endhint %}

### 오류 토스트로 구분하기

| 토스트 | 실패한 것 |
| --- | --- |
| `대시보드 요약 데이터를 불러오지 못했습니다.` | 대시보드 요약 |
| `인스턴스 목록을 불러오지 못했습니다.` | 인스턴스 목록 |
| `활동 로그를 불러오지 못했습니다.` | 이벤트 |
| `인스턴스 정보를 불러오지 못했습니다.` | 인스턴스 상세 |
| `고객사 목록을 불러오지 못했습니다.` | 고객사 |
| `사용자 목록을 불러오지 못했습니다.` | 사용자 |

{% hint style="warning" %}
**여러 화면에서 동시에 이 토스트가 뜨면 우리 쪽 장애**입니다. 즉시 에스컬레이션하십시오 ([17. 에스컬레이션](../part-4/17.-escalation.md)).
{% endhint %}

### 권한·세션 관련 응답

| 상황 | 화면 동작 |
| --- | --- |
| 권한 부족 | 오류 팝업 표시 후 **로그아웃** |
| 토큰 만료 | 자동 갱신 후 재시도. 실패하면 로그인 화면으로 |
| ADMIN 전용 경로에 USER 접근 | **403 화면** |

## 고객이 자주 묻는 것과 답

| 질문 | 답 |
| --- | --- |
| "저희 서버에 들어오는 건가요?" | 아닙니다. 고객사 → Poseidon **단방향**입니다. 인바운드 개방이 필요 없습니다 |
| "원격으로 제어하나요?" | 명령을 내리는 기능이 없습니다. 받기만 합니다 |
| "발송 데이터가 나가나요?" | 집계 수치와 예외 정보만 나갑니다. 수신번호·메시지 본문·DB 레코드는 전송 항목에 없습니다 |
| "우리 DB에 접근하나요?" | 접근하지 않습니다. 엔진이 이미 가진 지표를 요약해 보내는 것뿐입니다 |
| "실시간인가요?" | 30초 주기입니다. 장애 인지에는 최대 3\~4분이 걸립니다 |
| "연동이 끊기면 발송이 멈추나요?" | 멈추지 않습니다. 지표·감시만 중단됩니다 |
