# 10. 상태 판정 기준

고객 응대에서 가장 자주 쓰이는 지식입니다. **"왜 DOWN이라고 뜨는지", "왜 아직 UP인지"** 를 설명할 수 있어야 합니다.

## 기준값

| 판정              | 조건                            | 결과                        |
| --------------- | ----------------------------- | ------------------------- |
| **UP**          | 하트비트가 정상 수신되는 중               | 정상                        |
| **DOWN**        | 마지막 하트비트 후 **180초(3분)** 경과    | 장애 이벤트(CRITICAL) 생성 + 알림  |
| **UNKNOWN**     | 상태를 판정할 신호가 아직 없음             | 신규 등록 직후 등                |
| 정상 종료           | 고객사가 **종료 알림**을 보냄            | 계획된 종료로 기록 — **장애 알림 없음** |
| 오류 수집 지연(STALE) | 오류 수집 신호 180초 미수신             | 오류 수집 경로 이상 표시            |
| 오류 수집 불명(UNKNOWN) | 오류 수집 신호 **1,800초(30분)** 미수신  | 오류 수집 중단 상태 표시            |

### 반드시 기억할 3가지 숫자

| 숫자              | 의미                              |
| --------------- | ------------------------------- |
| **30초**         | 고객사가 하트비트를 보내는 주기 (기본값)         |
| **180초 (3분)**   | 이 시간 동안 신호가 없으면 DOWN            |
| **60초**         | 서버가 상태를 점검하는 주기                 |

{% hint style="info" %}
점검이 60초마다 돌기 때문에 **실제 화면에 DOWN이 뜨는 시각은 신호 끊김 후 3\~4분 뒤**입니다. 고객이 "10초 전에 껐는데 왜 아직 UP이냐"고 물으면 이 구조로 설명하십시오.
{% endhint %}

## 알림 동작

* 장애 이벤트가 생기면 담당자에게 알림이 발송됩니다.
* **같은 알림은 5분 단위로 묶여** 발송됩니다(알림 폭주 방지). 장애 하나에 알림이 1건만 온 것은 정상입니다.
* HA 이중화 고객사는 **노드마다 인스턴스가 별도**이므로, 두 노드가 같이 끊기면 알림도 2건입니다.

## 이벤트 종류

| 이벤트              | 심각도      | 언제                |
| ---------------- | -------- | ----------------- |
| 기동(STARTED)      | INFO     | 인스턴스가 기동 신호를 보냈을 때 |
| 종료(SHUTDOWN)     | WARN     | 정상 종료 신호를 보냈을 때   |
| 하트비트 타임아웃        | CRITICAL | 180초 미수신으로 DOWN 전환 |

## 제품별 판정 방식

| 모드          | 대상                             | 판정 방식                                                                    |
| ----------- | ------------------------------ | ------------------------------------------------------------------------ |
| **일반**      | Odyssey / Twoway (오류 수집 미사용)   | 하트비트만 봄                                                                  |
| **혼합**      | Odyssey / Twoway + 임베디드 Cypher | 하트비트 + 오류 수집 상태를 함께 갱신. 임베디드 Cypher는 별도 신호를 보내지 않고 Odyssey 하트비트 시점에 같이 갱신됨 |
| **로그 기반**   | M2X (레거시 + 사이드카 Cypher)        | 자체 하트비트가 없음. **생존 파일(`.alive`) 갱신 시각**(우선) 또는 **오류 로그 갱신 시각**(보조)이 300초 이내면 UP 유지 |

{% hint style="warning" %}
**M2X(로그 기반) 고객사는 판정 논리가 다릅니다.** 오류가 안 나는 조용한 시간대에는 신호가 약해 실제보다 상태가 나쁘게 보일 수 있습니다. M2X 고객 문의는 이 차이를 먼저 확인하고, 판단이 어려우면 개발팀에 확인하십시오.
{% endhint %}

## DOWN의 진짜 의미

{% hint style="danger" %}
`DOWN` = **"3분 넘게 상태 신호가 도달하지 않았다"** 입니다. **"문자 발송이 멈췄다"가 아닙니다.**
{% endhint %}

DOWN이 나오는 원인은 크게 4가지입니다.

| 원인                        | 발송은?      | 확인 방법                                            |
| ------------------------- | --------- | ------------------------------------------------ |
| Odyssey 프로세스가 실제로 중단됨     | 멈춤        | 고객사에 프로세스 상태 확인 요청                               |
| 고객사 서버 재기동 / 배포 작업 중      | 잠시 멈춤     | 작업 일정 확인. 끝나면 자동 복구                              |
| **아웃바운드 방화벽 차단 / 네트워크 순단** | **정상 발송** | 고객 로그의 `[Poseidon - heartbeat FAIL]` 확인          |
| 인증 키 비활성화(REVOKED)·만료     | **정상 발송** | [5. 인스턴스 관리](../part-2/5.-instances.md)에서 상태·활성 확인 |

그래서 고객에게는 이렇게 전달합니다.

> "상태 신호가 3분 이상 도달하지 않아 장애로 표시되었습니다. 실제 발송이 멈춘 것인지, 신호 경로만 막힌 것인지 확인이 필요합니다. Odyssey 로그에 `[Poseidon - heartbeat FAIL]` 이 남아 있는지 확인해 주시겠습니까?"

## 상태가 오락가락하는 경우

`UP` ↔ `DOWN` 이 반복되면 대부분 **네트워크 간헐 차단**입니다.

* 방화벽 정책이 일부 대역만 허용, 세션 타임아웃이 짧은 프록시 경유, 회선 불안정 등이 원인
* 발송에는 영향이 없지만 **알림 오탐**이 반복되므로 경로 안정화를 요청해야 합니다
* 조치 요청 대상: [14. 아웃바운드 방화벽 안내](../part-4/14.-firewall.md)

## 화면 값과의 대응

| 화면에서 보이는 것                    | 서버 판단                       |
| ----------------------------- | --------------------------- |
| 마지막 하트비트 `12초 전` (초록)         | 정상 수신 중                     |
| 마지막 하트비트 `5분 전` 이상 (빨강), 상태 UP | 곧 DOWN 전환 가능 — 신호가 이미 끊긴 상태 |
| 상태 `DOWN`                     | 180초 초과 확인됨                 |
| 상태 `UNKNOWN`                  | 판정 근거가 아직 없음                |
| 목록에 아예 없음                     | 기동 신호가 한 번도 오지 않음           |
