# 12. 오류 수집 구조와 Cypher

인스턴스 상세의 **`에러` 탭**이 어떻게 채워지는지, 왜 어떤 건 안 올라오는지를 설명합니다.

## 어떻게 수집되는가

고객사 엔진 안(또는 옆)에는 **Cypher**라는 오류 수집 모듈이 함께 동작합니다. 별도 에이전트 설치나 로그 파일 전송 없이, 엔진이 남기는 **ERROR / FATAL 로그를 가로채** Poseidon으로 보고합니다.

```
엔진 로그 발생 (ERROR/FATAL)
      │
      ├─ 발생 단계(서브시스템) 자동 분류
      ├─ 심각도 변환 (ERROR→ERROR, FATAL→CRITICAL)
      ├─ 동일 오류 30초 단위 묶음 처리
      ▼
 Poseidon 오류 보고 ──► DB 저장 ──► 인스턴스 상세 '에러' 탭
                                  + 이벤트 '에러 수신' + 알림
```

* `WARN` 이하 로그는 **수집 대상이 아닙니다.**
* 고객이 `poseidon.cypher.enabled: false` 로 설정하면 오류 수집만 끄고 상태·지표는 유지할 수 있습니다.

## Cypher 두 가지 모드

화면(**인스턴스 상세 → 개요 → Cypher 에이전트** 카드)에서 어느 모드인지 바로 보입니다. `에러` 탭 상단에도 `이 인스턴스의 에러는 [EMBEDDED] 모드 Cypher로 수집됩니다.` 처럼 표시됩니다.

| 항목 | **EMBEDDED** | **SIDECAR** |
| --- | --- | --- |
| 형태 | 네이티브 라이브러리 (`cypher.dll` / `libcypher.so`) | 별도 프로세스 |
| 위치 | 엔진과 **같은 프로세스** | 엔진 옆에서 로그 파일 감시 |
| 주 대상 | Odyssey / Twoway / CS | **M2X** (레거시) |
| 화면에 보이는 항목 | 호스트, 마지막 하트비트 | + **로그 파일 경로**, **마지막 `.alive` 체크**, **마지막 로그 활동** |
| 상태 판정 기여 | 엔진 하트비트에 동반 | **M2X의 UP/DOWN 판정 근거 그 자체** |

{% hint style="info" %}
**Cypher는 자동 감지 방식입니다.** 관제 측에서 켜고 끄는 토글이 없습니다. 고객사가 Cypher를 활성화하고 **첫 ERROR 또는 하트비트가 도착하면 화면에 자동으로 나타납니다.**

아직 신호가 없으면 카드에 이렇게 표시됩니다.
> Cypher 신호가 아직 감지되지 않았습니다. 고객사 측에서 Cypher를 활성화한 후 첫 ERROR 또는 heartbeat이 도착하면 자동으로 표시됩니다. 별도의 관제 토글은 없습니다.
{% endhint %}

### Cypher 상태 3가지

| 상태 | 의미 | 화면 |
| --- | --- | --- |
| `CONNECTED` | 정상 | 초록 |
| `STALE` | 응답이 임계 시간 이상 없음 | 주황 배너 — *Cypher 프로세스 중단 또는 네트워크 문제 가능성. 호스트에서 `journalctl -u cypher -f` 확인 권장.* |
| `UNKNOWN` | 상태 확인 불가 | 회색 배너 — *첫 하트비트 수신 대기 중이거나 연결이 끊긴 상태* |

`STALE`·`UNKNOWN`이면 인스턴스 상세 **상단에도 경고 배지**가 뜨고, 누르면 Cypher 카드로 스크롤됩니다.

## 심각도

| 화면 표시 | 원본 로그 레벨 | 의미 |
| --- | --- | --- |
| `ERROR` (주황) | ERROR | 처리 중 오류 발생 |
| `CRITICAL` (빨강) | FATAL | 심각 — 즉시 확인 필요 |

`에러` 탭의 심각도 필터에는 `CRITICAL`과 `ERROR`만 있습니다. WARN·INFO는 애초에 수집되지 않기 때문입니다.

{% hint style="info" %}
[5. 이벤트](../part-2/5.-events.md) 화면의 심각도 필터에는 `WARN` · `INFO`도 있습니다. 그건 **에러가 아니라 이벤트**(서비스 시작·종료 등)의 심각도이기 때문입니다. 두 화면의 필터가 다른 이유입니다.
{% endhint %}

## 서브시스템 (발생 단계)

오류가 어느 기능 영역에서 났는지 자동 분류된 값입니다. **원인 구간을 좁히는 데 가장 유용한 정보**이며, `에러` 탭에서 필터로 쓸 수 있습니다(수신된 값만 목록에 나타납니다).

| 서브시스템 | 의미 | 흔한 원인 |
| --- | --- | --- |
| `ODYSSEY_SEND` | 메시지 발송 단계 | 게이트웨이 응답 실패, 타임아웃 |
| `ODYSSEY_NETWORK` | 게이트웨이 HTTP 통신 | 대외 연동 구간 장애, 인증 만료, DNS·방화벽 |
| `ODYSSEY_DB` | DB 접근 | 커넥션 부족, 데드락, 쿼리 오류 |
| `ODYSSEY_COLLECT` | 발송 대상 수집 | DB 지연, 테이블·컬럼 설정 문제 |
| `ODYSSEY_FETCH` | 메시지 폴링 | 폴링 쿼리 오류, DB 부하 |
| `ODYSSEY_ROUTE` | 채널 라우팅 | 세션·계정 매핑 불일치 |
| `ODYSSEY_REPORT` | 발송 결과 반영 | 결과 업데이트 실패 |
| `ODYSSEY_AUTH` | 세션 인증 | 인증 파일(`.cert`)·계정 정보 문제 |
| `ODYSSEY_SCHEDULER` | 스케줄러 | 주기 작업 실패 |
| `ODYSSEY_MONITORING` | 모니터링 모듈 | 지표 수집 자체의 오류 |
| `ODYSSEY_STAT` | 통계 집계 | 집계 처리 실패 |
| `ODYSSEY_SHUTDOWN` | 종료 처리 | 종료 중 예외 |
| `ODYSSEY_CHARON` | Charon 모듈 | 해당 모듈 오류 |
| `ODYSSEY_PIPELINE` | 위에 해당하지 않는 전반 | 기타 |

## 묶음 처리(coalescing) — 건수가 실제와 다른 이유

동일한 오류가 폭주하면 **30초 윈도 안의 같은 오류를 1건으로 묶어** 보고합니다. 화면에서는 `×12` 같은 배지로 표시되고, 마우스를 올리면 `동일 에러 12건 묶음 (coalesced)` 툴팁이 나옵니다.

| 실제 상황 | 화면에 보이는 것 |
| --- | --- |
| DB 커넥션 장애로 같은 예외가 초당 수백 건 발생 | 30초 간격으로 1건씩, `×N` 배지에 누적 |
| 서로 다른 예외 3종이 발생 | 3건 각각 표시 |

{% hint style="info" %}
그래서 **화면의 에러 건수 ≠ 실제 발생 횟수** 입니다. 고객에게 "3건 발생했습니다"라고 말하지 말고 **"3종류의 오류가 반복 발생했습니다"** 로 전달하십시오.
{% endhint %}

## 스택 트레이스 읽는 법

에러 행을 펼치면 스택 트레이스가 나옵니다. 화면은 프레임을 두 종류로 나눕니다.

| 구분 | 기준 | 표시 |
| --- | --- | --- |
| **in-app** | `com.poseidon.*` / `com.kt.poseidon.*` | **기본으로 보임** (강조) |
| system | 그 외 (JDK, 프레임워크 등) | 접혀 있음 — `system 프레임 N개 표시` 버튼으로 펼침 |

{% hint style="success" %}
**개발팀 에스컬레이션 시에는 in-app 프레임 첫 줄이 가장 중요합니다.** 어느 클래스·메서드에서 났는지가 여기 있습니다.
{% endhint %}

## 오류가 안 올라오는 경우

| 원인 | 확인 방법 |
| --- | --- |
| **`에러` 탭 시간 필터가 기본 `24h`** | **`7d` 또는 `전체`로 바꿔보기 — 가장 흔한 원인** |
| Cypher 상태가 `STALE` / `UNKNOWN` | Cypher 카드 확인 → 고객사에 프로세스 상태 확인 요청 |
| Cypher 신호가 감지된 적 없음 | 카드에 `Cypher 신호가 아직 감지되지 않았습니다` → 고객 설정 확인 |
| 고객이 오류 수집을 껐음 (`cypher.enabled: false`) | 고객 설정 확인 |
| `libs/` 폴더의 네이티브 라이브러리 누락·손상 | 고객 기동 로그에 `[Cypher] 초기화 완료` 가 있는지 확인 |
| **인스턴스가 DOWN 상태** | DOWN 인 동안의 오류는 수집되지 않음 — **정상 동작** |
| 아웃바운드 차단 | 하트비트도 같이 끊겼는지 확인 ([15. 방화벽](../part-4/15.-firewall.md)) |
| 애초에 예외가 아닌 원인 | 설정 오류·발송 대상 없음 등은 ERROR 로그로 남지 않을 수 있음 |
| 30초 묶음 대기 중 | 최대 30초 지연은 정상 |

{% hint style="warning" %}
"에러가 안 보인다"는 문의를 받으면 **① 시간 필터 → ② Cypher 상태 → ③ 인스턴스 상태(DOWN?)** 순으로 3초 안에 확인하십시오. 대부분 여기서 끝납니다.
{% endhint %}

## 수집되는 항목 / 수집되지 않는 항목

**수집되는 것**

| 항목 | 예 |
| --- | --- |
| 심각도 | `ERROR` / `CRITICAL` |
| 서브시스템 | `ODYSSEY_SEND` |
| 예외 클래스 | `java.net.SocketTimeoutException` |
| 예외 메시지 | 로그에 기록된 메시지 |
| 스택트레이스 요약 | 발생 지점 식별용 요약 (전문 아님) |
| 발생 시각 | 최초 발생 시각 |
| 발생 횟수 | 묶음 처리된 건수 (`×N`) |

**수집되지 않는 것**

{% hint style="success" %}
수신자 전화번호, 메시지 본문, 발송 대상 데이터, 고객사 DB 레코드, DB·게이트웨이 계정 **비밀번호/시크릿**은 **전송 항목에 없습니다.**

(CS 서비스의 경우 화면에도 명시되어 있습니다 — *계정 식별자만 저장됩니다. 비밀번호/시크릿은 전송되지 않습니다.*)
{% endhint %}

{% hint style="warning" %}
단, **예외 메시지와 스택트레이스 요약은 전송**됩니다. 고객사가 로그에 개인정보를 남기는 구성이라면 그 문자열이 함께 전달될 수 있습니다. 보안 검토에서 이 질문이 나오면 숨기지 말고 그대로 설명하고, 필요 시 오류 수집만 비활성화(`poseidon.cypher.enabled: false`)할 수 있다고 안내하십시오.
{% endhint %}

## 중복 오류 처리

같은 오류가 여러 번 보고되어도 서버가 중복을 걸러 **한 행의 발생 횟수(`×N`)와 발생 시각만 갱신**할 수 있습니다. 그래서 "새 오류가 안 생기는데 상황은 계속된다"는 경우, **기존 행의 `×N` 숫자와 `발생` 시각이 올라가고 있는지** 확인해야 합니다.
