# 11. 오류 수집 구조

인스턴스 상세 화면의 **오류 로그**가 어떻게 채워지는지, 왜 어떤 건 안 올라오는지를 설명합니다.

## 어떻게 수집되는가

고객사 Odyssey 안에는 **Cypher**라는 오류 수집 모듈이 함께 동작합니다(`libs/` 폴더의 네이티브 라이브러리). 별도 에이전트 설치나 로그 파일 전송 없이, Odyssey가 남기는 **ERROR / FATAL 로그를 가로채** Poseidon으로 보고합니다.

```
Odyssey 로그 발생 (ERROR/FATAL)
      │
      ├─ 발생 단계(서브시스템) 자동 분류
      ├─ 심각도 변환 (ERROR→ERROR, FATAL→CRITICAL)
      ├─ 동일 오류 30초 단위 묶음 처리
      ▼
 Poseidon 오류 보고 ──► DB 저장 ──► 인스턴스 상세 "오류 로그" 표 + 알림
```

* `WARN` 이하 로그는 **수집 대상이 아닙니다.**
* 고객이 `poseidon.cypher.enabled: false` 로 설정하면 오류 수집만 끄고 상태·지표는 유지할 수 있습니다.

## 심각도

| 화면 표시            | 원본 로그 레벨 | 의미                  |
| ---------------- | -------- | ------------------- |
| `ERROR` (주황)     | ERROR    | 처리 중 오류 발생          |
| `CRITICAL` (빨강)  | FATAL    | 심각 — 즉시 확인 필요       |

## 서브시스템 (발생 단계)

오류가 어느 기능 영역에서 났는지 자동 분류된 값입니다. **원인 구간을 좁히는 데 가장 유용한 정보**입니다.

| 서브시스템               | 의미            | 흔한 원인                       |
| ------------------- | ------------- | --------------------------- |
| `ODYSSEY_SEND`      | 메시지 발송 단계     | 게이트웨이 응답 실패, 타임아웃           |
| `ODYSSEY_NETWORK`   | 게이트웨이 HTTP 통신 | 대외 연동 구간 장애, 인증 만료, DNS·방화벽 |
| `ODYSSEY_DB`        | DB 접근         | 커넥션 부족, 데드락, 쿼리 오류          |
| `ODYSSEY_COLLECT`   | 발송 대상 수집      | DB 지연, 테이블·컬럼 설정 문제         |
| `ODYSSEY_FETCH`     | 메시지 폴링        | 폴링 쿼리 오류, DB 부하             |
| `ODYSSEY_ROUTE`     | 채널 라우팅        | 세션·계정 매핑 불일치                |
| `ODYSSEY_REPORT`    | 발송 결과 반영      | 결과 업데이트 실패                  |
| `ODYSSEY_AUTH`      | 세션 인증         | 인증 파일(`.cert`)·계정 정보 문제     |
| `ODYSSEY_SCHEDULER` | 스케줄러          | 주기 작업 실패                    |
| `ODYSSEY_MONITORING` | 모니터링 모듈       | 지표 수집 자체의 오류               |
| `ODYSSEY_STAT`      | 통계 집계         | 집계 처리 실패                    |
| `ODYSSEY_SHUTDOWN`  | 종료 처리         | 종료 중 예외                     |
| `ODYSSEY_CHARON`    | Charon 모듈     | 해당 모듈 오류                    |
| `ODYSSEY_PIPELINE`  | 위에 해당하지 않는 전반 | 기타                          |

## 묶음 처리(coalescing) — 건수가 실제와 다른 이유

동일한 오류가 폭주하면 **30초 윈도 안의 같은 오류를 1건으로 묶어** 보고합니다(발생 횟수 N으로 집계).

| 실제 상황                       | 화면에 보이는 것                    |
| --------------------------- | ---------------------------- |
| DB 커넥션 장애로 같은 예외가 초당 수백 건 발생 | 30초 간격으로 1건씩 (발생 횟수에 누적)     |
| 서로 다른 예외 3종이 발생             | 3건 각각 표시                     |

{% hint style="info" %}
그래서 **화면의 오류 건수 ≠ 실제 발생 횟수** 입니다. 고객에게 "3건 발생했습니다"라고 말하지 말고 "3종류의 오류가 반복 발생했습니다"로 전달하십시오.
{% endhint %}

## 오류가 안 올라오는 경우

| 원인                            | 확인 방법                                             |
| ----------------------------- | ------------------------------------------------- |
| 고객이 오류 수집을 껐음 (`cypher.enabled: false`) | 고객 설정 확인                                          |
| `libs/` 폴더의 네이티브 라이브러리 누락·손상  | 고객 기동 로그에 `[Cypher] 초기화 완료` 가 있는지 확인              |
| **인스턴스가 DOWN 상태**             | DOWN 인 동안의 오류는 수집되지 않음 — **정상 동작**                |
| 아웃바운드 차단                      | 하트비트도 같이 끊겼는지 확인 ([14. 방화벽](../part-4/14.-firewall.md)) |
| 애초에 예외가 아닌 원인                 | 설정 오류·발송 대상 없음 등은 ERROR 로그로 남지 않을 수 있음            |
| 30초 묶음 대기 중                   | 최대 30초 지연은 정상                                     |

## 수집되는 항목 / 수집되지 않는 항목

**수집되는 것**

| 항목        | 예                                    |
| --------- | ------------------------------------ |
| 심각도       | ERROR / CRITICAL                     |
| 서브시스템     | `ODYSSEY_SEND`                       |
| 예외 클래스    | `java.net.SocketTimeoutException`    |
| 예외 메시지    | 로그에 기록된 메시지                          |
| 스택트레이스 요약 | 발생 지점 식별용 요약 (전문 아님)                 |
| 발생 시각     | 최초 발생 시각                             |
| 발생 횟수     | 묶음 처리된 건수                            |

**수집되지 않는 것**

{% hint style="success" %}
수신자 전화번호, 메시지 본문, 발송 대상 데이터, 고객사 DB 레코드, DB·게이트웨이 계정 정보는 **전송 항목에 없습니다.**
{% endhint %}

{% hint style="warning" %}
단, **예외 메시지와 스택트레이스 요약은 전송**됩니다. 고객사가 로그에 개인정보를 남기는 구성이라면 그 문자열이 함께 전달될 수 있습니다. 보안 검토에서 이 질문이 나오면 숨기지 말고 그대로 설명하고, 필요 시 오류 수집만 비활성화(`poseidon.cypher.enabled: false`)할 수 있다고 안내하십시오.
{% endhint %}

## 중복 오류 처리

같은 오류가 여러 번 보고되어도 서버가 중복을 걸러 **한 행에 발생 횟수만 증가**시킬 수 있습니다. 그래서 "새 오류가 안 생기는데 상황은 계속된다"는 경우, 기존 행의 발생 시각·횟수가 갱신되고 있는지 확인해야 합니다.
