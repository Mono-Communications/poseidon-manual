# 11. 상태 판정 기준

고객 응대에서 가장 자주 쓰이는 지식입니다. **"왜 DOWN이라고 뜨는지", "왜 아직 UP인지"** 를 설명할 수 있어야 합니다.

## <mark style="color:blue;">기준값</mark>

***

| 판정       | 조건                         | 결과                                                                                                           |
| -------- | -------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **UP**   | 하트비트가 정상 수신되는 중            | 정상                                                                                                           |
| **DOWN** | 마지막 하트비트 후 **180초(3분)** 경과 | 이벤트 <mark style="color:red;">**`하트비트 타임아웃`**</mark>(CRITICAL) 생성 + 알림                                        |
| 정상 종료    | 고객사가 **종료 알림**을 보냄         | 이벤트 <mark style="color:red;">`서비스 종료`</mark>(WARN) — **장애 알림 없음**                                            |
| 복구       | 끊겼다가 신호가 다시 옴              | <mark style="color:red;">이벤트</mark> <mark style="color:red;"></mark><mark style="color:red;">**`복구`**</mark> |

### <mark style="color:cyan;">기억할 3가지 숫자</mark>

***

| 숫자            | 의미                      |
| ------------- | ----------------------- |
| **30초**       | 고객사가 하트비트를 보내는 주기 (기본값) |
| **180초 (3분)** | 이 시간 동안 신호가 없으면 DOWN    |
| **60초**       | 서버가 상태를 점검하는 주기         |

{% hint style="info" %}
점검이 60초마다 돌기 때문에 **실제 화면에 DOWN이 뜨는 시각은 신호 끊김 후 3\~4분 뒤**입니다. 고객이 "10초 전에 껐는데 왜 아직 UP이냐"고 물으면 이 구조로 설명하십시오.
{% endhint %}

## <mark style="color:blue;">화면에서 UP/DOWN의 두 가지 뜻</mark>

***

{% hint style="danger" %}
**같은** <mark style="color:red;">**`UP`**</mark><mark style="color:red;">**/**</mark><mark style="color:red;">**`DOWN`**</mark>**&#x20;글자가 화면마다 다른 것을 뜻합니다. 이 구분을 못 하면 고객에게 잘못된 답을 하게 됩니다.**

두 화면의 숫자가 달라도 오류가 아닙니다. **"엔진이 지금 살아있냐"는 질문은 반드시** [**4. 인스턴스**](../part-2/4.-instances.md) **화면으로 답하십시오.**
{% endhint %}

| 화면                        | `UP`의 의미                          | `DOWN`의 의미                                                     |
| ------------------------- | --------------------------------- | -------------------------------------------------------------- |
| **대시보드 · 인스턴스 · 인스턴스 상세** | 하트비트 수신 중 = **엔진 생존**             | 180초 이상 신호 없음                                                  |
| **고객사 상세**                | 등록 **`APPROVED`** + **활성 플래그 ON** | 등록 <mark style="color:red;">**`APPROVED`**</mark> + 활성 플래그 OFF |

## <mark style="color:blue;">하트비트 경과 시간 색상</mark>

***

인스턴스 화면의 **`하트비트`** 열은 경과 시간에 따라 색이 달라집니다.

| 경과        | 색  | 의미                    |
| --------- | -- | --------------------- |
| **2분 이내** | 초록 | 정상 수신 중               |
| **2\~5분** | 주황 | **주의** — 이미 신호가 늦고 있음 |
| **5분 초과** | 빨강 | 신호 끊김                 |

{% hint style="info" %}
상태가 아직 **`UP`**&#xC778;데 하트비트가 주황·빨강이면 **곧 DOWN으로 넘어갈 가능성**이 큽니다. 선제 대응할 수 있는 신호입니다.
{% endhint %}

## <mark style="color:blue;">Cypher 에이전트 상태</mark>

***

오류 수집 경로가 살아있는지를 나타내는 **별도 상태**입니다. 엔진 상태(UP/DOWN)와 다릅니다.

| 상태              | 의미                                  | 화면    |
| --------------- | ----------------------------------- | ----- |
| **`CONNECTED`** | 정상                                  | 초록    |
| **`STALE`**     | 임계 시간 이상 응답 없음 — 프로세스 중단·네트워크 문제 의심 | 주황 배너 |
| **`UNKNOWN`**   | 첫 하트비트 대기 중이거나 연결 끊김                | 회색 배너 |

{% hint style="warning" %}
**엔진은** <mark style="color:red;">`UP`</mark>**인데 Cypher가** <mark style="color:red;">`STALE`</mark>**인 조합이 가능합니다.** 이 경우 감시는 되지만 **오류가 안 올라옵니다.** 고객이 "에러가 났는데 화면에 없다"고 하면 여기부터 확인하십시오.
{% endhint %}

## <mark style="color:blue;">**제품별 판정 방식**</mark>

***

| 모드        | 대상                                          | 판정 방식                                                                     |
| --------- | ------------------------------------------- | ------------------------------------------------------------------------- |
| **일반**    | Odyssey / Twoway / CS (Cypher 미사용)          | 하트비트만 봄                                                                   |
| **혼합**    | Odyssey / Twoway / CS + **EMBEDDED** Cypher | 하트비트 + 오류 수집 상태를 함께 갱신. EMBEDDED Cypher는 별도 신호를 보내지 않고 엔진 하트비트 시점에 같이 갱신됨 |
| **로그 기반** | **M2X** (레거시 + **SIDECAR** Cypher)          | 자체 하트비트가 없음. **`.alive` 파일 갱신 시각**(우선) 또는 **로그 활동 시각**(보조)으로 상태를 추정       |

{% hint style="danger" %}
**M2X는 판정 논리가 다릅니다.** 화면에서 M2X 인스턴스에는 `Limited Visibility` 배지가 붙어 있고, 마우스를 올리면 이렇게 나옵니다.

> M2X 인스턴스는 자체 라이프사이클 신호가 없습니다. 상태는 Cypher heartbeat + 로그 활동으로 추정합니다.

오류가 안 나는 조용한 시간대에는 신호가 약해 **실제보다 상태가 나쁘게 보일 수 있습니다.** M2X 문의는 인스턴스 상세 → Cypher 카드의 **`마지막 .alive 체크`** 를 먼저 확인하고, 판단이 어려우면 연구소팀에 확인하십시오.
{% endhint %}

## <mark style="color:blue;">알림 동작</mark>

***

* 장애 이벤트가 생기면 담당자에게 알림이 발송됩니다.
* **같은 알림은 5분 단위로 묶여** 발송됩니다(알림 폭주 방지). 장애 하나에 알림이 1건만 온 것은 정상입니다.
* HA 이중화 고객사는 **노드마다 인스턴스가 별도**이므로, 두 노드가 같이 끊기면 알림도 2건입니다.

{% hint style="warning" %}
알림 수신처·임계값을 화면에서 조정하는 기능은 **없습니다** ([9. 설정](../part-2/9.-settings.md) 알림 = 준비 중). 요청은 연구소팀에 접수합니다.
{% endhint %}

## <mark style="color:blue;">DOWN의 진짜 의미</mark>

***

{% hint style="danger" %}
<mark style="color:red;">**`DOWN`**</mark> = **"3분 넘게 상태 신호가 도달하지 않았다"** 입니다. **"발송이 멈췄다"가 아닙니다.**
{% endhint %}

DOWN이 나오는 원인은 크게 4가지입니다.

| 원인                        | 발송은?      | 확인 방법                                                                           |
| ------------------------- | --------- | ------------------------------------------------------------------------------- |
| **엔진 프로세스가 실제로 중단됨**      | 멈춤        | 고객사에 프로세스 상태 확인 요청                                                              |
| **고객사 서버 재기동 / 배포 작업 중**  | 잠시 멈춤     | 작업 일정 확인. 끝나면 자동 복구                                                             |
| 아웃바운드 방화벽 차단 / 네트워크 순단    | **정상 발송** | 고객 로그의 `[`<mark style="color:red;">**`Poseidon - heartbeat FAIL`**</mark>`]` 확인 |
| **인증 키 해지(`REVOKED`)·만료** | **정상 발송** | [7. 인스턴스 관리](../part-2/7.-admin-instances.md)에서 상태·활성 확인                        |

**정상 종료인지 장애인지는** [**5. 이벤트**](../part-2/5.-events.md)**에서 가릅니다.**

| 이벤트                     | 판정                        |
| ----------------------- | ------------------------- |
| **`서비스 종료`** (SHUTDOWN) | 고객사가 **정상적으로 껐음** — 장애 아님 |
| **`하트비트 타임아웃`**         | **신호가 끊김** — 조사 필요        |

## <mark style="color:blue;">상태가 오락가락하는 경우</mark>

***

`UP` ↔ `DOWN` 이 반복되면 대부분 **네트워크 간헐 차단**입니다.

* 방화벽 정책이 일부 대역만 허용, 세션 타임아웃이 짧은 프록시 경유, 회선 불안정 등이 원인
* 발송에는 영향이 없지만 **알림 오탐**이 반복되므로 경로 안정화를 요청해야 합니다
* [5. 이벤트](../part-2/5.-events.md)에서 해당 고객사로 필터를 걸면 `하트비트 타임아웃` ↔ `복구`가 반복되는 패턴이 바로 보입니다
* 조치 요청 대상: [15. 아웃바운드 방화벽 안내](../part-4/15.-firewall.md)

## <mark style="color:blue;">화면 값과의 대응</mark>

***

| 화면에서 보이는 것                     | 서버 판단                        |
| ------------------------------ | ---------------------------- |
| **하트비트 `12초 전` (초록)**          | 정상 수신 중                      |
| **하트비트 `3분 전` (주황)**           | 신호가 늦고 있음 — 곧 DOWN 가능        |
| **하트비트 `5분 전` 이상 (빨강), 상태 UP** | 이미 끊긴 상태, 다음 점검에서 DOWN 전환 예정 |
| **상태 `DOWN` + 옆의 경과 시간**       | 180초 초과 확인됨, 끊긴 지 그만큼 지남     |
| **하트비트 열에 시각(`14:02`)**        | **DOWN 상태** — 그 시각이 마지막 수신   |
| **`-`**                        | 한 번도 수신되지 않음                 |
| **목록에 아예 없음**                  | 기동 신호가 한 번도 오지 않음            |

## <mark style="color:blue;">가동률(24h)에 대한 주의</mark>

***

{% hint style="danger" %}
인스턴스 상세의 **`가동률 (24h)`은 실측값이 아닙니다.** 최근 24시간의 종료·타임아웃 이벤트 **1건당 5분 중단**으로 환산한 추정치입니다.

* 실제로 3시간 끊겨도 이벤트가 1건이면 `99.7%`로 나옵니다.
* **고객에게 이 수치를 SLA 근거로 인용하지 마십시오.**
* 실제 중단 구간은 이벤트 탭에서 **`서비스 종료`/`하트비트 타임아웃` → `복구`/`서비스 시작`** 시각을 직접 대조해 산출합니다.
{% endhint %}
