## 개발팀으로 넘기는 것

| 상황 | 이유 |
| --- | --- |
| 설정·활성 상태를 다 확인했는데도 `status=401/403` 이 계속됨 | 인증 키 자체 또는 게이트웨이 문제 |
| 상태는 `UP` 인데 **지표 그래프만** 계속 비어 있음 | 지표 파이프라인(브로커·수집기) 문제 |
| **여러 고객사가 동시에** `DOWN` 또는 지표 누락 | 플랫폼 장애 의심 |
| **여러 화면에서 동시에** 조회 실패 토스트 | 웹·API 장애 |
| 화면 상태가 실제와 계속 어긋남 | 판정 로직·데이터 문제 |
| 화면 자체가 안 열림 / 로그인 불가 | 웹·API 장애 |
| **비밀번호 초기화**가 필요한 계정 | 화면에 기능 없음 |
| **사용자 역할(ADMIN ↔ USER) 변경** | 화면에 기능 없음 |
| **알림 수신처·임계값 조정** | 화면에 기능 없음 (서버 설정) |
| **7일보다 오래된 이벤트 이력 조회** | 화면 조회 범위 밖 |
| 고객사명·고객사 키 **수정** | 화면에 수정 기능 없음 |
| M2X(로그 기반) 고객사의 상태 판정 이슈 | 판정 방식이 달라 확인 필요 |
| 고객사가 프록시 경유·목적지 IP 고정·HTTPS 전용 등 예외 구성 요구 | 네트워크 구성 협의 필요 |
| API 키 발급 모달에서 **`닫고 폐기`로 인스턴스가 삭제된 뒤 복구가 필요한 경우** | 재생성으로 해결되지 않는 상황 확인 필요 |

### 이관 시 첨부할 내용

```
① 고객사명 / 인스턴스 ID (인스턴스 상세 '기본 정보'에서 확인)
② 서비스 타입 (ODYSSEY / TWOWAY / CS / M2X)
③ 발생 시각 (분 단위) 및 지속 여부
④ 화면에서 보이는 상태
   - [4. 인스턴스]  : UP/DOWN, 마지막 하트비트
   - [7. 인스턴스 관리] : 등록 상태(PENDING/APPROVED/…), 활성 여부
   - 인스턴스 상세  : Cypher 모드·상태, 최근 에러의 예외 클래스와 서브시스템
⑤ 고객 로그의 [Poseidon / [Cypher 포함 라인
⑥ 고객 설정의 poseidon 블록 (인증 키는 앞 8자리만)
⑦ 최근 고객사 작업 여부 (배포·재시작·네트워크 변경)
⑧ HA 여부 / 영향 노드
```

## 알려진 제약 — 고객에게 단정하면 안 되는 것

| 항목 | 현재 상태 | 응대 방법 |
| --- | --- | --- |
| **알림 설정 화면** | `COMING SOON` — 이메일/Slack/Webhook/알림 규칙/조용한 시간 모두 준비 중. 상단바 🔔 아이콘도 미동작 | "화면에서 알림을 설정할 수 있다"고 말하지 말 것. 요청은 개발팀 접수 |
| **가동률(24h)** | 이벤트 건수 × 5분으로 환산한 **추정치** | **SLA 근거로 인용 금지.** 실제 중단 구간은 이벤트 시각으로 산출 |
| **API 키 재확인** | 발급 순간에만 전체 키 확인 가능, 이후 키 접두사만 조회 | 분실 시 **재발급** 안내. "다시 알려드릴 수 있다"고 말하지 말 것 |
| **`닫고 폐기` 버튼** | 신규 생성 건에서 누르면 인스턴스를 해지 후 **삭제** | 발급 모달에서 버튼 글자를 반드시 확인 |
| **이벤트 조회 범위** | 최근 **7일**, 최대 **500건** | 그 이전 이력은 개발팀 조회 요청 |
| **에러 탭 기본 필터** | **24시간** | "에러가 없다"고 답하기 전에 `전체`로 바꿔 확인 |
| **AI 오류 분석** | 오류 수집·저장·이력 조회까지 동작. 분석은 축적된 데이터를 활용하는 단계 | "오류 이력을 분석에 활용합니다" 수준으로 설명. **"AI가 자동 조치한다"는 표현 금지** |
| **지표 유실** | 브로커 전송 실패 시 재시도 후 드랍(생존 기록은 유지) | "지표는 유실될 수 있으나 생존 감시는 유지됩니다" |
| **원격 설정 변경** | 기능 없음 | 고객사가 직접 `config/system.yml` 수정 + 재시작해야 함 |
| **고객사 정보 수정** | 등록만 가능, 수정 기능 없음 | 잘못 입력하면 개발팀 요청 |
| **HA 노드별 키 정책** | 노드별 발급 여부는 건별 확인 필요 | 단정하지 말고 확인 후 회신 |
| **목적지 주소·포트** | 운영 환경(온프레미스/클라우드)에 따라 다름 | 매뉴얼 값 복사 금지, 해당 고객사 발급값 확인 |
| **자동 갱신 없는 화면** | 고객사·고객사 상세·인스턴스 관리·사용자·설정 | 진행 중 장애 추적 시 `새로고침` 필요 |
| **DOWN의 의미** | "신호 미도달"이지 "발송 중단"이 아님 | 반드시 구분해 전달 |
| **고객사 상세의 UP/DOWN** | **등록·활성 기준**이며 하트비트 기준이 아님 | 가동 여부는 [4. 인스턴스](../part-2/4.-instances.md)로 답할 것 |
| **M2X 상태** | 자체 신호 없이 `.alive`·로그 활동으로 **추정** | 조용한 시간대 오판 가능. 단정 금지 |

## 판단이 어려울 때의 기본 원칙

{% hint style="info" %}
1. **화면 값을 근거로만 말합니다.** 추측한 원인을 고객에게 단정하지 않습니다.
2. **발송 영향 여부를 먼저 가릅니다.** "신호만 끊긴 것"과 "발송이 멈춘 것"은 고객에게 완전히 다른 사안입니다.
3. **정상 종료인지 타임아웃인지 이벤트로 확인합니다.** 이걸 안 하고 장애로 연락하면 신뢰를 잃습니다.
4. **여러 고객사에서 동시에 발생하면 우리 문제**로 보고 즉시 에스컬레이션합니다.
5. 애매하면 [16. 플레이북](16.-playbook.md)의 7가지 정보를 모아 넘깁니다.
{% endhint %}
