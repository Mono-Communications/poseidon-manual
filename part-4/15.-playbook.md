# 15. 증상별 대응 플레이북

문의를 받았을 때 순서대로 따라가는 진단 절차입니다. 각 절차의 목표는 **"우리 문제 / 고객 설정 문제 / 고객 네트워크 문제 / 실제 장애"** 중 무엇인지 3분 안에 가르는 것입니다.

## 공통 1단계 — 화면에서 먼저 확인

| 확인          | 화면                                                |
| ----------- | ------------------------------------------------- |
| 인스턴스가 목록에 있는가 | [4. Odyssey 모니터링](../part-2/4.-monitoring.md)      |
| 상태와 마지막 하트비트 | 동일                                                |
| 등록 상태·활성 여부 | [5. 인스턴스 관리](../part-2/5.-instances.md)            |
| 오류 로그 마지막 항목 | 인스턴스 상세                                           |

## A. "연동했는데 화면에 안 뜬다"

```
고객 로그에 [Poseidon - start] 가 있는가?
├─ 없음 ─────────► poseidon.enabled=false / url 미설정 / 재시작 안 함
│                  → 설정 확인 + 재시작 요청
└─ 있음
   ├─ SUCCESS ──► 인스턴스 관리에서 상태 확인
   │              ├─ REVOKED·비활성 → 활성화
   │              └─ APPROVED  → 대시보드 필터·고객사명 확인 → 그래도 없으면 에스컬레이션
   └─ FAIL
      ├─ Connection timed out / No route to host → 아웃바운드 차단 (방화벽)
      ├─ Connection refused                     → 목적지 포트 오류
      ├─ Could not resolve host                 → DNS
      ├─ status=401 / 403                       → 인증 키 문제
      └─ status=404                             → url 경로 오류
                                                  (/api/v1/odyssey-instances 로 끝나야 함)
```

{% hint style="success" %}
**FAIL 로그에 HTTP 상태 코드(4xx)가 있으면 방화벽은 열린 것**이고, timeout·no route 계열이면 네트워크 차단입니다.
{% endhint %}

## B. "고객은 정상이라는데 DOWN 알림이 왔다"

1. 마지막 하트비트 시각 확인 — **3분 이상 끊긴 구간이 실제로 있었는가**
2. 그 시각에 고객사 네트워크 작업·방화벽 정책 변경·프록시 재기동·배포가 있었는가
3. 재시작 없이 다시 `UP` 으로 돌아왔는가 → **네트워크 순단** 가능성 (발송은 정상이었을 것)
4. 반복되면 아웃바운드 경로 안정성 점검 요청 ([14. 방화벽](14.-firewall.md))

전달 화법:

> "Odyssey는 정상이었지만 상태 신호가 3분간 도달하지 못해 장애로 판정했습니다. 발송에는 영향이 없었고, 신호 경로만 점검하면 됩니다."

## C. "상태는 UP인데 지표 그래프가 비어 있다"

* 상태·오류와 지표는 **경로가 다릅니다** ([9. 시스템 구성](../part-3/9.-architecture.md))
* 고객 쪽 문제가 아닐 가능성이 큽니다 → **우리 쪽 지표 파이프라인 확인 필요 → 개발팀 에스컬레이션**
* 단, 고객사 Odyssey 버전이 낮아 지표를 실어 보내지 않는 경우도 있으므로 **버전을 함께 확인**하십시오

## D. "오류 로그가 안 올라온다"

| 확인 순서                                  | 판정                     |
| -------------------------------------- | ---------------------- |
| 1. 고객 기동 로그에 `[Cypher] 초기화 완료` 가 있는가   | 없으면 오류 수집 비활성 또는 라이브러리 누락 |
| 2. 고객 설정 `poseidon.cypher.enabled`     | `false` 면 정상 동작(수집 안 함) |
| 3. `libs/` 폴더에 `cypher.dll` / `libcypher.so` 존재 | 누락이면 패키지 재배포 필요        |
| 4. 인스턴스 상태가 `DOWN` 인가                  | DOWN 중에는 오류를 받지 않음 — 정상 |
| 5. 최근 30초 이내 발생인가                      | 묶음 처리로 최대 30초 지연 — 정상  |
| 6. 기존 행의 발생 시각·횟수가 갱신되고 있는가            | 중복 오류는 새 행이 아니라 기존 행 갱신 |

## E. "1대는 되는데 1대는 안 된다" (HA)

* 거의 항상 **한쪽 노드 방화벽 누락** 또는 **한쪽 노드 설정 미반영**입니다
* 확인: 인스턴스 관리에서 해당 고객사 인스턴스가 2건 `APPROVED`·활성인지 → 모니터링에서 2건 보이는지
* 안 보이는 노드의 로그에서 `[Poseidon - start]` 유무 확인

## F. "알림이 안 온다 / 너무 많이 온다"

| 증상        | 확인                                                                 |
| --------- | ------------------------------------------------------------------ |
| 안 온다      | 테넌트 관리자 이메일, 고객 설정 `contact-email` 확인. 그래도 안 오면 알림 채널 문제 → 에스컬레이션 |
| 너무 많이 온다  | 같은 알림은 5분 단위로 묶입니다. **서로 다른 인스턴스·오류는 각각 발송** — HA 2노드면 2건이 정상      |

## G. "발송이 안 되는데 화면은 전부 정상(UP·오류 없음)"

Poseidon은 **엔진 생존과 예외**를 봅니다. 아래는 예외 없이도 발송이 안 되는 경우입니다.

| 가능성                    | 확인 방향                                     |
| ---------------------- | ----------------------------------------- |
| 발송 대상 데이터가 없음          | 고객사 DB에 발송 요청이 들어왔는지                      |
| 발송 금지 시간·채널 설정 문제      | Odyssey 설정(발송 규격·세션) — 상세 화면의 **발송 규격** 대조 |
| 게이트웨이 측 지연 (예외는 아직 없음) | 지표의 응답 지연·큐 적체 추이 확인                      |
| 계정·세션 한도               | 고객사 계약·계정 설정 확인                           |

이 경우는 화면만으로 결론이 안 나므로, 고객사 로그와 함께 개발팀에 확인 요청하는 편이 빠릅니다.

## H. "기동 직후 이상한 경고가 보인다"

고객 로그에 하트비트 관련 "인스턴스 미존재" 경고가 한두 번 찍히는 것은 **기동 등록과 첫 하트비트가 거의 동시에 도착했을 때 나오는 정상 동작**입니다. 다음 주기에 자동으로 정상화되므로 조치 불필요합니다.

## 문의 접수 시 반드시 받아둘 정보

```
1. 고객사명 / 인스턴스 ID
2. 증상 발생 시각 (분 단위)
3. 증상: 화면에서 무엇이 어떻게 보이는가
4. 고객 로그의 [Poseidon / [Cypher 포함 라인
5. 최근 고객사 작업 여부 (배포·재시작·네트워크 변경)
6. HA 여부 및 어느 노드인지
```

이 6가지가 있으면 대부분 이 페이지 안에서 분류가 끝나고, 안 되면 그대로 개발팀에 넘기면 됩니다 ([16. 에스컬레이션](16.-escalation.md)).
