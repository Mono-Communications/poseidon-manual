# 16. 증상별 대응 플레이북

문의를 받았을 때 순서대로 따라가는 진단 절차입니다. 각 절차의 목표는 **"**<mark style="color:red;">**우리 문제 / 고객 설정 문제 / 고객 네트워크 문제 / 실제 장애**</mark>**"** 중 무엇인지 3분 안에 가르는 것입니다.

| --------------------- | --------------------------------------------- |
| **인스턴스가 목록에 있는가**     | [4. 인스턴스](../part-2/4.-instances.md)          |

{% endhint %}

## <mark style="color:blue;">A. "연동했는데 화면에 안 뜬다"</mark>

***

```
고객 로그에 [Poseidon - start] 가 있는가?
├─ 없음 ─────────► poseidon.enabled=false / url 미설정 / 재시작 안 함
│                  → 설정 확인 + 재시작 요청
└─ 있음
   ├─ SUCCESS ──► [7. 인스턴스 관리]에서 상태 확인
   │              ├─ PENDING          → 승인 필요 (우리 쪽 처리 누락!)
   │              ├─ REVOKED/REJECTED → 재발급 또는 재승인
   │              └─ APPROVED         → [4. 인스턴스] 필터·검색 확인
   │                                    → 그래도 없으면 에스컬레이션
   └─ FAIL
      ├─ Connection timed out / No route to host → 아웃바운드 차단 (방화벽)
      ├─ Connection refused                     → 목적지 포트 오류
      ├─ Could not resolve host                 → DNS
      ├─ status=401 / 403                       → 인증 키 문제
      └─ status=404                             → url 경로 오류
                                                  (/api/v1/odyssey-instances 로 끝나야 함)
```

{% hint style="success" %}
**FAIL 로그에 HTTP 상태 코드(4xx)가 있으면 방화벽은 열린 것**이고, timeout·no route 계열이면 네트워크 차단입니다.
{% endhint %}

{% hint style="warning" %}
[4. 인스턴스](../part-2/4.-instances.md)에서 안 보인다고 결론 내리기 전에 **서비스 필터와 상태 필터가 걸려 있지 않은지** 확인하십시오. 대시보드 KPI를 클릭해 들어오면 필터가 이미 걸린 상태입니다.
{% endhint %}

## <mark style="color:blue;">B. "고객은 정상이라는데 DOWN 알림이 왔다"</mark>

***

1. [5. 이벤트](../part-2/5.-events.md)에서 해당 고객사 필터 → <mark style="color:red;">**`서비스 종료`**</mark>**인지&#x20;**<mark style="color:red;">**`하트비트 타임아웃`**</mark>**인지 확인**
   * <mark style="color:red;">**`서비스 종료`**</mark> → **정상 종료.** 고객사 계획 작업. 장애 아님 → 여기서 종료
   * <mark style="color:red;">**`하트비트 타임아웃`**</mark> → 아래 계속
2. 마지막 하트비트 시각 확인 — **3분 이상 끊긴 구간이 실제로 있었는가**
3. 그 시각에 고객사 네트워크 작업·방화벽 정책 변경·프록시 재기동·배포가 있었는가
4. 재시작 없이 다시 <mark style="color:red;">**`UP`**</mark> 으로 돌아왔는가 (이벤트에 <mark style="color:red;">**`복구`**</mark>) → **네트워크 순단** 가능성 (발송은 정상이었을 것)
5. 반복되면 아웃바운드 경로 안정성 점검 요청 ([15. 방화벽](15.-firewall.md))

## <mark style="color:blue;">**C. "상태는 UP인데 지표 그래프가 비어 있다"**</mark>

***

* 상태·오류와 지표는 **경로가 다릅니다** ([10. 시스템 구성](../part-3/10.-architecture.md))
* 고객 쪽 문제가 아닐 가능성이 큽니다 → **우리 쪽 지표 파이프라인 확인 필요 → 연구소팀 에스컬레이션**
* 단, 고객사 엔진 버전이 낮아 지표를 실어 보내지 않는 경우도 있으므로 [**4. 인스턴스**](../part-2/4.-instances.md)**의 `버전` 열을 함께 확인**하십시오

## <mark style="color:cyan;">E. "1대는 되는데 1대는 안 된다" (HA)</mark>

***

* 거의 항상 **한쪽 노드 방화벽 누락** 또는 **한쪽 노드 설정 미반영**입니다
* 확인 ①: [6. 고객사](../part-2/6.-tenants.md) 상세 → **인스턴스 헬스맵** 카드 수가 노드 수와 맞는가
* 확인 ②: [7. 인스턴스 관리](../part-2/7.-admin-instances.md)에서 해당 고객사 인스턴스가 노드 수만큼 `APPROVED`·활성인가
* 확인 ③: [4. 인스턴스](../part-2/4.-instances.md)에서 몇 건이 `UP`인가
* 안 보이는 노드의 로그에서 **`[Poseidon - start]`** 유무 확인

## <mark style="color:cyan;">F. "알림이 안 온다 / 너무 많이 온다"</mark>

<table><thead><tr><th width="141.5">증상</th><th>확인</th></tr></thead><tbody><tr><td><strong>안 온다</strong></td><td>고객사 대표 이메일(<a href="../part-2/6.-tenants.md">6. 고객사</a>), 고객 설정 <mark style="color:red;"><strong><code>contact-email</code></strong></mark> 확인. 그래도 안 오면 알림 채널 문제 → 에스컬레이션</td></tr><tr><td><strong>너무 많이 온다</strong></td><td>같은 알림은 5분 단위로 묶입니다. <strong>서로 다른 인스턴스·오류는 각각 발송</strong> — HA 2노드면 2건이 정상</td></tr></tbody></table>

{% hint style="danger" %}
**알림 수신처·임계값을 화면에서 조정할 수 없습니다.** [9. 설정](../part-2/9.-settings.md)의 알림 섹션은 `COMING SOON` 상태입니다. 고객에게 "설정에서 끌 수 있다"고 안내하지 마십시오.
{% endhint %}

## <mark style="color:cyan;">G. "발송이 안 되는데 화면은 전부 정상(UP·오류 없음)"</mark>

Poseidon은 **엔진 생존과 예외**를 봅니다. 아래는 예외 없이도 발송이 안 되는 경우입니다.

<table><thead><tr><th width="199">가능성</th><th>확인 방향</th></tr></thead><tbody><tr><td><strong>발송 대상 데이터가 없음</strong></td><td>고객사 DB에 발송 요청이 들어있는지</td></tr><tr><td><strong>채널·세션 설정 문제</strong></td><td>인스턴스 상세의 <strong>세션 정보</strong> 탭에서 채널별 전송 규격·세션이 계약과 맞는지 대조</td></tr><tr><td><strong>계정·세션 한도</strong></td><td>고객사 계약·계정 설정 확인</td></tr><tr><td>Cypher가 <strong><code>STALE</code></strong></td><td>오류가 나고 있는데 <strong>보고만 안 되는</strong> 상태일 수 있음 → Cypher 카드 확인</td></tr></tbody></table>

이 경우는 화면만으로 결론이 안 나므로, 고객사 로그와 함께 연구소팀에 확인 요청하는 편이 빠릅니다.

## <mark style="color:cyan;">H. "M2X 고객사 상태가 이상하다"</mark>

***

{% hint style="warning" %}
M2X는 **자체 신호가 없어 추정으로 판정**합니다 ([11. 상태 판정 기준](../part-3/11.-status.md)).
{% endhint %}

1. 인스턴스명 옆 <mark style="color:red;">**`Limited Visibility`**</mark> 배지 확인 → M2X 맞는지
2. 인스턴스 상세 → 개요 → **Cypher 에이전트 카드**
3. <mark style="color:red;">**`마지막 .alive 체크`**</mark> 시각 확인 — 이 값이 M2X UP/DOWN의 핵심 근거
4. <mark style="color:red;">**`마지막 로그 활동`**</mark>도 확인 — 조용한 시간대에는 신호가 약해 실제보다 나쁘게 보일 수 있음
5. Cypher 모드가 `SIDECAR`인지 확인
6. 판단이 어려우면 연구소팀 확인 요청

## <mark style="color:cyan;">I. "기동 직후 이상한 경고가 보인다"</mark>

고객 로그에 하트비트 관련 "인스턴스 미존재" 경고가 한두 번 찍히는 것은 **기동 등록과 첫 하트비트가 거의 동시에 도착했을 때 나오는 정상 동작**입니다. 다음 주기에 자동으로 정상화되므로 조치 불필요합니다.

## <mark style="color:cyan;">J. "화면이 안 열린다 / 숫자가 안 나온다"</mark>

| 증상                    | 판정                                                                          |
| --------------------- | --------------------------------------------------------------------------- |
| **특정 카드만 비고 나머지는 정상** | 해당 조회만 실패 — 토스트 문구로 어느 것인지 확인 ([10. 시스템 구성](../part-3/10.-architecture.md)) |
| **`403` 화면이 뜸**       | **ADMIN 전용 화면에 USER로 접근** — 정상 동작                                           |
| **갑자기 로그인 화면으로 튕김**   | 유휴 30분 / 토큰 만료 / 다른 탭 로그아웃                                                  |
| 여러 화면에서 동시에 조회 실패     | 우리 쪽 장애 → **즉시 에스컬레이션**                                                     |
| **고객사 화면 숫자가 안 바뀜**   | 고객사·인스턴스 관리·사용자 화면은 **자동 갱신이 없음** → `새로고침`                                  |

## <mark style="color:cyan;">문의 접수 시 반드시 받아둘 정보</mark>

```
1. 고객사명 / 인스턴스 ID   ← 인스턴스 상세 '개요 → 기본 정보'에 있음
2. 증상 발생 시각 (분 단위)
3. 증상: 화면에서 무엇이 어떻게 보이는가
4. 고객 로그의 [Poseidon / [Cypher 포함 라인
5. 최근 고객사 작업 여부 (배포·재시작·네트워크 변경)
6. HA 여부 및 어느 노드인지
7. 서비스 타입 (ODYSSEY / TWOWAY / CS / M2X)
```
