# 14. 아웃바운드 방화벽 안내

Poseidon 연동에서 고객사가 유일하게 **네트워크 작업**을 해야 하는 부분이며, 연동 실패의 대부분이 여기서 발생합니다. 이 페이지 내용은 고객사 보안·네트워크 담당자에게 그대로 전달할 수 있습니다.

## 왜 아웃바운드가 필요한가

Poseidon은 고객사 서버 상태를 **가져오는(pull) 방식이 아니라, Odyssey가 보내는(push) 방식**으로 수집합니다. 즉 고객사에서 나가는 경로가 열려 있지 않으면 감시 기능이 전혀 동작하지 않습니다.

이 구조 덕분에 보안 관점에서 아래가 보장됩니다.

| 항목         | 내용                                     |
| ---------- | -------------------------------------- |
| 통신 방향      | 고객사 → Poseidon **단방향**                 |
| 인바운드 포트 개방 | **불필요** — Poseidon이 고객사로 접속하는 경로가 없음   |
| 원격 제어      | 없음 — 명령 전달·설정 변경 기능이 없음                |
| VPN / 전용선  | 불필요 — HTTP(S) 아웃바운드만으로 동작              |
| 대상 범위      | 지정된 단일 호스트·포트 1개소로 한정                  |
| 고객사 DB 접근  | 없음                                     |

## 차단되어 있으면 잃는 것

Odyssey의 발송은 계속 동작하지만 **모니터링 기능이 전부 무력화**됩니다.

| 잃는 것         | 구체적 영향                                                  |
| ------------ | ------------------------------------------------------- |
| 생존 감시        | 엔진이 중단되어도 알 수 없음 → 장애 인지가 고객 문의 시점까지 지연                 |
| 지표 축적        | 큐 적체·응답 지연·실패율 상승 같은 **선행 징후 관측 불가** → 선제 조치 불가         |
| 오류 수집·분석     | 예외 이력이 남지 않음 → 사후 원인 분석도 고객사 로그를 직접 받아야만 가능             |
| 장애 알림        | 담당자 알림 미발송                                              |
| 복구 시간(MTTR)  | 근거 데이터가 없어 추정에 의존 → 원인 규명·복구 지연                         |

{% hint style="warning" %}
**부분 차단(간헐적 드롭)이 더 골치 아픕니다.** 정상 가동 중인데도 하트비트 미수신으로 `DOWN` 오탐이 반복되어, 알림 신뢰도가 떨어집니다. 안정적인 경로 확보가 오탐 방지에도 필요합니다.
{% endhint %}

## 차단 상태여도 발송에는 영향 없음

Poseidon 전송은 발송 파이프라인과 분리된 전용 스레드에서 수행되며, 실패 시 경고 로그만 남기고 넘어갑니다. **방화벽이 닫혀 있거나 Poseidon이 점검 중이어도 문자 발송은 정상 진행**됩니다. 다만 그 기간의 지표·오류 이력은 유실됩니다.

이 점을 먼저 말해주면 고객 보안팀의 경계심이 크게 낮아집니다.

## 방화벽 신청 정보 (고객 전달용)

```
[방화벽 허용 요청]
- 출발지 : 고객사 Odyssey 설치 서버 (HA 구성 시 양 노드 모두)
- 목적지 : {{Poseidon 호스트}} / TCP {{포트}}
- 프로토콜 : TCP / HTTP(S)
- 방향   : Outbound only (Inbound 불필요)
- 주기   : 30초 간격 상시 + 오류 발생 시
- 규모   : 회당 300~500B, 일 약 1~1.5MB
- 용도   : 발송 엔진 운영 지표·장애 정보 전송 (모니터링)
```

| 항목    | 값                                    |
| ----- | ------------------------------------ |
| 출발지   | 고객사 Odyssey 설치 서버 IP (**HA면 양 노드**)  |
| 목적지   | 환경별로 다름 — 담당자가 확인해 기재                |
| 포트    | 환경별로 다름 (HTTPS 443 또는 지정 포트)         |
| 방향    | **Outbound only**                    |
| 주기    | 30초 간격 상시                            |
| 트래픽   | 회당 300\~500B, 일 1\~1.5MB             |

{% hint style="info" %}
목적지 주소·포트는 **운영 환경(온프레미스/클라우드)에 따라 다릅니다.** 매뉴얼 값을 그대로 복사하지 말고 해당 고객사에 발급된 값을 확인해 기재하십시오. 프록시 경유, 목적지 IP 고정, HTTPS 전용 등 예외 구성 요청은 개발팀과 협의합니다.
{% endhint %}

## 경로 개방 점검 (고객사 서버에서 실행)

```bash
# 1) 목적지 포트 도달 여부
curl -v -m 5 http://{{ip}}:{{port}}/api/v1/dashboard/summary

# 2) 인증 키 유효성
curl -i -m 5 -X POST \
  -H "X-AUTH-KEY: {{발급받은 인증 키}}" \
  -H "Content-Type: application/x-protobuf" \
  http://{{ip}}:{{port}}/api/v1/odyssey-instances/heartbeats
```

| 결과                                          | 판정                                |
| ------------------------------------------- | --------------------------------- |
| HTTP 응답 코드 수신 (200 / 400 / 401 등)           | **경로 개방 정상** — 이후는 설정·인증 문제       |
| `Connection timed out` / `No route to host` | 아웃바운드 차단 — 방화벽 정책 확인 필요           |
| `Connection refused`                        | 목적지 포트 오류 — 주소·포트 재확인             |
| `Could not resolve host`                    | DNS 해석 실패 — 내부 DNS 또는 hosts 등록 필요 |

## 고객 로그로 판별하기

고객사 Odyssey 로그에서 아래 문자열을 확인하면 방화벽 문제인지 바로 구분됩니다.

| 로그                                        | 판정               |
| ----------------------------------------- | ---------------- |
| `[Poseidon - heartbeat] OK`               | 정상 — 경로 열려 있음    |
| `[Poseidon - heartbeat FAIL] Connection timed out` | **아웃바운드 차단 의심**  |
| `[Poseidon - heartbeat FAIL] No route to host` | **아웃바운드 차단 의심**  |
| `[Poseidon - start FAIL] status=401`      | 경로는 열림, **인증 키 문제** |
| `[Poseidon - start FAIL] status=404`      | 경로는 열림, **URL 경로 오류** |
| 로그가 아예 없음                                 | 연동 비활성 상태 또는 재시작 안 함 |

{% hint style="success" %}
**FAIL 로그에 HTTP 상태 코드가 찍혀 있으면 방화벽은 열린 것입니다.** 상태 코드가 없고 timeout·no route 계열이면 네트워크 차단입니다. 이 한 가지 기준만 알아도 문의의 절반은 즉시 분류할 수 있습니다.
{% endhint %}

## HA 이중화 주의

* 두 노드가 **각각 독립적으로** 전송합니다 → 방화벽도 양쪽 다 필요
* 한쪽만 열면 화면에는 인스턴스 1개만 `UP` 으로 보입니다
* "1대는 되는데 1대는 안 된다"는 문의는 거의 항상 **한쪽 노드 방화벽 누락**입니다
